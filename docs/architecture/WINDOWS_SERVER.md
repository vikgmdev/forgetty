# Forgetty server on Windows (design, decided 2026-10-26)

Goal: local shells on Windows live in a per-user Forgetty server, as on Linux, so they survive closing the window. Phones and other devices can attach to it over iroh when the user opts in.

## Decisions
1. Data plane: protocol v2 over iroh on loopback (`127.0.0.1:<port>`, relays off, address pinned). No new IPC data protocol. The in-process ConPTY `LocalBackend` stays as a fallback and for the smoke.
2. Control plane: a named pipe `\\.\pipe\forgetty-<user SID>-<secret>` serving the existing forgetty-socket JSON-RPC (made transport-generic). User-only DACL, `reject_remote_clients`, first-pipe-instance, client token SID check on the server, server PID token SID check on the client (squatting).
3. Local trust: the app auto-pairs through the pipe (`pair_open` with a short ttl, then pair/2 over loopback). The local app device shows as "This PC (local app)" and is not offered for revoke (same-user processes can always re-pair, same trust domain as the Linux socket).
4. ConPTY: a small own wrapper in forgetty-pty for Windows (the `windows` crate), with no INHERIT_CURSOR and no WIN32_INPUT_MODE. Still strip `CSI ?9001 h/l` before the byte log as a guard. Job Object per pane with KILL_ON_JOB_CLOSE (tree kill), plus one server-wide job so a server crash kills children. Exit watcher on the process handle. Ctrl+C as 0x03. `CancelSynchronousIo` for a blocked writer.
5. State: `%LOCALAPPDATA%\forgetty\server`, separate from the client folder (`%APPDATA%\forgetty`). Protected user-only DACLs through a Windows implementation in `forgetty-core::fsutil` (move the helpers from `clients/windows/remote/src/acl.rs`). Fix the wrong doc at `platform.rs:313`.
6. Binaries: the server/CLI is `forgetty.exe` (same CLI as Linux: `forgetty server run|start|stop|status`, `forgetty pair`, `forgetty ls`, ...). The app is `forgetty-win.exe`. The MSI stops installing a copy of the app as `forgetty.exe`. `ghostty-vt.dll` next to both.
7. Reachability: loopback only by default. Binding other addresses (`bind_addrs`) is an explicit opt-in in config, with the firewall prompt as the user's choice.
8. Lifetime: a HKCU Run key starts `forgetty server start` at login. The app also starts it on demand and restarts it when connect fails. No scheduled task, no service.
9. Logoff and reboot: panes die, cold restore re-spawns from the saved layout (same as Linux without linger). The server saves and freezes the layout when Windows announces the end of the session, so the dying shells do not shrink it.
10. Cwd: spawn cwd only in the first release. Live cwd via the PEB is a later item.
11. Server-side argv rules on Windows: PATH-only lookup, no UNC, device or `\??\` paths (port `clients/windows/shell-core/src/resolve.rs` rules), because remote clients can send argv.

## Status (WP0 to WP3)
Done: WP0 to WP5. Server crates check and test in the `server-crates` job of `.github/workflows/windows-client.yml`.

- The control pipe is `\\.\pipe\forgetty-<SID>-<secret>`. `<secret>` is 128 random bits (hex) in `pipe.secret` in the server's data folder. The server makes a new secret at every start, under the state lock and before it binds, and writes it with a temporary file in the same folder and a rename (`fsutil::write_private_atomic`), so a reader sees the old file or the new one and never a half-written one. The CLI reads the file and retries when it is empty or short, it never deletes it. Pipe names are listable by any user on the machine (`\\.\pipe\` is a shared namespace), so the name is not a secret from other users. What the secret does is stop a squat that is prepared before the next start: another process cannot create the next pipe name in advance, because the name does not exist until the server has started. The real protection is the owner and DACL of the pipe, the client check by the server, and the server check by the client (below). The secret is kept out of logs and CLI error text (the name is shown as `forgetty-<SID>-<redacted>`). A server started with `--state-dir` has its own data folder, so its own secret and pipe. Code: `crates/forgetty-socket/src/pipe.rs` (server), `crates/forgetty-server/src/pipe_client.rs` (CLI), `crates/forgetty-server/src/sockpath_windows.rs` (names and secret).
- The pipe is created with an explicit owner and one DACL entry: `O:<SID>D:P(A;;GA;;;<SID>)`, with `first_pipe_instance`, `reject_remote_clients` and no inherited access.
- Elevation: the server does not run elevated. `forgetty server run` with an elevated token exits with code 78 (`EXIT_CONFIG`) and a message, before it makes any state. A normal process of the same user could otherwise use an elevated server to run commands as administrator, around the UAC prompt. There is no `-elevated` pipe name and no mandatory label. The tests set `FORGETTY_TEST_ALLOW_ELEVATED=1` because the CI runner is an administrator (debug builds only: a release build ignores it). An elevated app uses the in-process ConPTY (`LocalBackend`), so its panes end when its window closes (no survival).
- The client keeps one integrity rule: `PipeStream::connect` refuses a server whose integrity level is below the client's, so a lower-level process cannot stand in for the server of an elevated client. It also reads the pipe owner (`GetSecurityInfo` on the client handle) and requires it to be the user SID, on top of the process-id check.
- The server check of the client SID runs after the first read from the connection, because Windows refuses `ImpersonateNamedPipeClient` before that. Until then nothing the client sent reaches a handler and nothing is written back, and the connection is not counted by `is_attached` (the count starts once the client has been verified).
- The client check of the server runs in `PipeStream::connect` before the first byte is sent: the pipe owner must be the current user's SID, the process behind `GetNamedPipeServerProcessId` must run as the current user, and its integrity level must not be lower than the client's. The test `connect_checks_the_server_level_in_both_directions` (`pipe_client.rs`) covers both directions with a client level override.
- Logoff and shutdown: a hidden top-level window on its own thread (`crates/forgetty-server/src/endsession.rs`) gets `WM_QUERYENDSESSION` and `WM_ENDSESSION`. It has to be a top-level window: message-only windows are not sent the end-of-session messages. The query is answered "yes" and nothing else. When `WM_ENDSESSION` says the session really ends (`wParam` not zero), the callback calls `SessionManager::begin_shutdown` first and then writes the layout with `save_layout_final` (the normal `save_layout` does nothing once frozen), so the shells that die with the session cannot shrink the saved layout between the two. A cancelled end (`wParam` zero) changes nothing. The handler logic has a unit test.
- Job Objects: the server job and every pane job have `JOB_OBJECT_LIMIT_BREAKAWAY_OK` next to `KILL_ON_JOB_CLOSE`, so a program that asks for `CREATE_BREAKAWAY_FROM_JOB` can leave the job.
- Argv rules (WP4, `resolve_program` in `crates/forgetty-pty/src/process_windows.rs`): a program with a path separator that is relative, a UNC path, and the prefixes `\\?\`, `\\.\` and `\??\` are refused, and so is a drive-relative path such as `C:foo`. A `.bat` or `.cmd` target is refused when any argument holds a cmd metacharacter (`& | < > ^ % ! " ( )` or a newline), because `cmd.exe` would parse them. Each rule has a test.
- Packaging (WP5): the per-user MSI installs `forgetty-win.exe` (the app), `forgetty.exe` (the CLI and server, built from `forgetty-server`) and one `ghostty-vt.dll` that both load. `forgetty.exe` is no longer a copy of the app. The install folder is on the user PATH. The HKCU Run value `Forgetty server` runs `"<install>\forgetty.exe" server start` at login (the start call detaches the server and returns). An immediate custom action runs `forgetty.exe server stop` before an uninstall or an upgrade, so the exe is not in use. Uninstall removes the Run value and keeps the server's data. The installer job checks the files, the Run value, `forgetty.exe --version`, and that a release `forgetty.exe server run` exits 78 on the elevated runner. Known edge: the Run entry starts a console program, so a console window can flash for a moment at login. An upgrade from a build older than WP5, where `forgetty.exe` was a copy of the app, would start that app in the stop step: those builds were not released.
- Stop across integrity levels: `forgetty server stop` on Windows uses `PipeStream::connect_for_shutdown`. It checks the pipe owner and the user of the server process like every connection, but accepts a server at a LOWER integrity level than the CLI. Reason: msiexec can run elevated (a UAC install) while the server never does, and the normal rule refuses a lower server, so the stop would fail without a message and Restart Manager would ask to close programs or reboot. The call sends `shutdown` only, takes the server pid from the pipe (not from an answer of the server), and uses nothing but the ack. No other request may use that connection type. Test: `connect_checks_the_server_level_in_both_directions`, and the installer job stops a real medium-integrity server from the elevated runner (uninstall and upgrade).
- Upgrade and uninstall stop the server. The shells of its panes end with it. At the next start the saved layout is restored cold (new shells in the saved folders), so a running command is lost. The install ends by running the app's start-server switch, which starts the server again for the user (it ends with exit 1 and starts nothing when the installer itself is elevated, because the server does not run elevated; the Run value starts it at the next login).
- Saving the layout at logoff: `save_layout` and `save_layout_final` make their snapshot while holding the save lock (`save_session_for_with`), and `save_layout` checks `is_shutting_down` under the lock. A save that started before the freeze cannot write an older state over the final one.
- Default shell: `shell` in `config.toml`, then `FORGETTY_SHELL`, then `pwsh.exe`, `powershell.exe`, `%COMSPEC%`. Programs are found by walking PATH in Rust (no `where`).

### Manual test: a client of another user is refused
CI has one account, so the cross-user case is by hand (needs an administrator to make the second account):
1. In an elevated shell: `net user fgtest P@ssw0rd-Test1 /add`.
2. As your own user: `forgetty server start`, then `forgetty server status` (running).
3. As the other user: `runas /user:fgtest cmd` and in that shell run `forgetty server status`. Expected: the open of `\\.\pipe\forgetty-<your SID>` fails with "Access is denied" (the DACL), and the CLI says the server is not reachable. The other user also computes a different pipe name (its own SID), so it does not even try yours.
4. To see the server-side SID check as well, start the server with a DACL that is too wide (a test build) or use the unit test `a_client_of_another_user_gets_no_service` in `crates/forgetty-socket/tests/pipe_server.rs`, which makes the server expect the SYSTEM SID.
5. Cleanup: `forgetty server stop`, `net user fgtest /delete`.

### Manual test: the server refuses to run elevated
1. In an elevated shell: `forgetty --state-dir C:\fgtest server run`. Expected: exit code 78 (`echo %ERRORLEVEL%`) and a message that the server does not run elevated.
2. In a normal shell: `forgetty --state-dir C:\fgtest server start` works as usual. Cleanup: `forgetty --state-dir C:\fgtest server stop`.

### Manual test: logoff keeps the layout
1. In a normal shell: `forgetty server start`, open three panes (`forgetty new`), check `forgetty ls`.
2. Sign out and sign in again, then `forgetty server start`. Expected: the three panes are restored from the saved layout, not one or none.

## For WP6 (the Windows client)
- An elevated app does not use the server. It uses the in-process ConPTY (`LocalBackend`), and its panes end when the window closes. Say so in the first-run text and in the settings.
- The supervisor starts the server only from a normal process. If `forgetty server run` exits with 78, fall back to the in-process backend and do not retry.
- Do not log or show the pipe name. Read `pipe.secret` fresh at every connect (the secret changes at every server start) and retry a few times when the file is empty or short. A missing file means no server has started yet.
- The client must verify the server the way the CLI does (pipe owner, process user, integrity not below its own). The shared code is `crates/forgetty-server/src/pipe_client.rs`.
